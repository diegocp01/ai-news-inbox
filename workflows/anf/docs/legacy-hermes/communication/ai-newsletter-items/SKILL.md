# AI Newsletter Items

Use this skill whenever the user asks for `Anf:`, `anf:`, or an AI-newsletter-format item from a URL, topic, X post, screenshot, or brief claim.

## Required Output Format

Return exactly this four-line block, with no extra commentary:

```text
Title: [neutral newsletter-style title]
URL: [final learn-more URL]
Image URL: [real image URL]
Summary: [≤60-word summary]
```

## the user's Format Preferences

- Keep the title neutral and newsletter-like; avoid hype, dunking, or social-media phrasing.
- Keep the summary at **60 words maximum**.
- Prefer a clean final/source URL over tracking URLs.
- Apply the machine-readable `metadata.hermes.anf_policy` to final URLs and image URLs.
- If no compliant alternate exists, leave `URL:` empty rather than using a forbidden final URL.
- Image URL must be a real URL, never a placeholder. Apply `anf_policy.forbidden_image_domains`; if no article image exists, find a suitable company/product logo.

## Workflow

1. Identify the underlying news item.
   - For a URL: fetch metadata first (`og:title`, `og:description`, `og:image`, `og:url`) and then inspect page/readme/body text if needed. When the user supplies a direct official URL as a correction, inspect it before relying on any prior search result; a current primary launch page supersedes stale coverage that reported an earlier delay, preview, or rumor.
   - For a corrected pending ANF, replace the queued block rather than retaining both the superseded claim and its correction; verify the retained record contains the exact final four-line block before delivery.
   - Treat browser navigation as stateful: never batch multiple `browser_navigate` calls in parallel when later metadata inspection depends on the active page. Navigate to one candidate, then immediately read its canonical URL, OpenGraph metadata, and images before navigating elsewhere.
   - If `browser_navigate` times out but its error payload reports a resolved title or URL, immediately probe the current page with `browser_console` before retrying or switching sources. The navigation may have completed despite the timeout; recover canonical metadata and body text from the live DOM when available.
   - If ordinary extraction fails or the page is JavaScript-rendered, open it in the browser and read metadata from the live DOM. If browser loading is blocked, fetch the HTML with a realistic user agent and parse the same metadata rather than relying only on search snippets.
   - For a Cloudflare-blocked page whose body was verified through another path, use Microlink (`https://api.microlink.io/?url=<encoded-url>`) as a metadata fallback. Require `status: success`, inspect the returned image type and dimensions, and verify relevance; Microlink supplies metadata, not independent reporting.
   - For a GitHub repo: use repo OpenGraph metadata plus README summary. When rendered README images resolve through expiring `private-user-images.githubusercontent.com` URLs with signed query strings, inspect the raw `README.md` and use its stable `https://github.com/user-attachments/assets/<id>` URL instead; verify that the stable URL redirects to the intended image and record its dimensions.
   - For an X screenshot or X-only claim: use X Search and/or X public embed metadata to identify the original post, author, and any linked official/company page. Treat X Search’s generated synthesis as discovery only: verify quoted wording, product details, benchmark numbers, incident causes, availability, and outbound URLs against the actual post, official page, repository, or independent coverage before publishing. Discard unsourced elaborations and any response that role-plays the product instead of reporting search evidence.
   - If X Search is unavailable or returns weak synthesis, inspect a public timeline mirror for the named official account to recover current post text, timestamps, and status IDs; treat the mirror as discovery, not independent confirmation. Then fetch each candidate `https://x.com/i/status/<id>` with a realistic user agent and parse `og:title`, `og:description`, and `og:image`. This can recover the author and exact post text even when `cdn.syndication.twimg.com/tweet-result` returns only `{}`. Treat recovered social metadata as primary-post evidence, but still enforce the final URL and image-domain policy.
   - For screenshot follow-ups, treat a terse correction or label from the user (for example, “App blocks”) as the intended feature name. Re-anchor the item around that feature rather than broad visual similarity, then search the exact visible UI phrase in quotes. If no durable public announcement exists, preserve rollout uncertainty and leave `URL:` blank instead of attaching a merely adjacent article.
   - In an active ANF exchange, treat a newly attached news screenshot with no accompanying text as a new ANF intake; extract, verify, queue, and return the four-line block without asking whether the user wants ANF formatting.
2. Pick the final URL.
   - Prefer article/company/project/repo pages.
   - Enforce the machine-readable `anf_policy` in frontmatter rather than duplicating mutable domain rules in runtime logic.
   - When an official company page is disallowed by policy, prefer an official GitHub repository or strong independent coverage; if no compliant alternate exists, leave `URL:` blank.
3. Pick and verify the image URL.
   - Prefer a story-specific article OpenGraph image or an informative in-article figure over a generic company logo.
   - Reject image hosts listed in `anf_policy.forbidden_image_domains`; find a publisher, company, or product image instead.
   - Decode HTML entities in copied metadata URLs (for example, convert `&amp;` to `&`) before output.
   - Verify that the final image URL resolves directly to an image; when several candidates exist, compare relevance and dimensions before choosing.
   - Prefer navigating directly to the image URL in the browser for this check. A browser image document whose title reports the filename and dimensions (for example, `story.webp (2400×1260)`) is sufficient verification; do not add an unnecessary local download or shell probe that can trigger approval and delay an otherwise complete ANF intake.
   - If the item is about a company and no story-specific image is available, use the official logo URL from the company site as a last resort.
4. Write the summary.
   - One sentence is usually enough.
   - Mention AI relevance clearly.
   - Preserve uncertainty with words like “reportedly,” “claims,” or “says” when the source is self-reported or not independently verified.

## Claim-Verification Patterns

- **Live leaderboards:** Inspect the rendered live leaderboard rather than relying only on articles, search snippets, or server-side extraction, which can lag a JavaScript-updated board. Record the exact category, leaderboard date, total votes, model votes, displayed rank, rank spread, score with uncertainty, comparison score, price fields, and any “preliminary” label. For alternate views such as Pareto, activate the visible UI control and then verify the resulting route and rendered text; a direct URL or scripted click can fail to update client state while leaving stale content visible. Read the chart’s stated price formula before comparing costs—for example, a blended price at a specified input/output ratio is not the same as either posted input or output token price. Describe the result as a ranking on that specific benchmark—not general model superiority—and note that crowdsourced rankings can change. For Arena video claims, open the dedicated modality route (for example, `/leaderboard/text-to-video`, `/leaderboard/image-to-video`, or `/leaderboard/video-edit`) rather than the generic leaderboard. Overlapping rank spreads or score intervals mean “listed first” is safer than “undisputed best,” even when point estimates differ.
- **Generative-video model launches and product-surface drift:** Verify the exact model name and separate full-model availability from individual features exposed in consumer apps. Check whether the complete model is available through APIs, AI Studio, enterprise platforms, or creator tools while only one capability (such as scene extension) appears in the Gemini app. Report scene length/context, keyframe interpolation, draft resolution and speed/cost claims, upscaling limits, reference-video support, plan eligibility, and rollout geography only when the launch page states them. Do not compress “a feature is in Gemini” into “the whole model lives in Gemini.”
- **Generative-music model families and licensing:** Enumerate each model variant, its intended role, and free-versus-paid access instead of treating a family name as one model. Verify which training inputs are licensed, opt-in, or user-supplied; distinguish models shipping now from future artist-likeness or remix products; and state whether older models are being retired. Attribute quality and competitor-superiority claims to the vendor, and preserve unresolved copyright litigation as context only when material to the launch.
- **Interactive-reasoning agent benchmarks:** Separate the agent harness from its underlying model and report the benchmark split exactly (public, semi-private, private, or competition set). Verify the metric—not just the headline percentage—plus environments, levels, action count, observation format, reasoning setting, and whether comparisons are controlled ablations. For ARC-AGI-3, distinguish a 100.00 RHAE score on the public set from performance on hidden competition sets; name the model powering the harness and state that the result evaluates the complete agent system, not the model alone. Check for editor’s notes that narrow earlier wording.
- **Temporary API and credit price reductions:** Distinguish API token pricing, prepaid/product credits, and subscription usage allowances. Verify the exact model, percentage reduction, duration, effective timing, eligible products or plans, rollout language, and any explicitly unchanged subscriptions. Do not imply that a temporary API/credit discount makes every consumer plan cheaper or raises included usage limits.
- **Policy, procurement, and court-ruling claims:** Read the operative order, statute, or opinion before compressing a headline. Distinguish a supplier's designation as a risk from proof that its product is inherently dangerous; identify the issuing agency, legal authority, affected systems and contracts, and whether contractors are barred only while performing work for that agency. Separate private use and unrelated federal contracts from the covered procurement scope—“entire supply chain” can otherwise imply a nationwide ban. Verify when the designation began versus when a court upheld, blocked, or stayed it; check parallel cases under different legal authorities, dissenting opinions, and remaining appeals before calling a ruling final. State whether a restriction is proposed, effective, stayed, or under review, and distinguish an agency's stated rationale from the court's holding and the company's response.
- **Cross-company safety coordination:** Distinguish a formal partnership or newly created organization from exploratory talks, an informal working group, shared evaluations, or coordination through an existing forum. Verify who publicly confirmed the activity, how long it has been under way, the proposed scope, whether participants have agreed on governance or enforcement, and whether the body actually exists. Use “coordination,” “working together,” or “discussed creating” unless the evidence establishes a signed partnership or launched institution; this prevents tentative cooperation from becoming a completed deal.
- **Vertical model configurations:** Distinguish a domain-specific configuration from a newly trained model. Verify the underlying model, added indexes/tools, system instructions, settings, plugins, data controls, and exact access path separately. Preserve staged availability—such as selected firms now and API access coming later—and report private-benchmark gains only with the benchmark set, baseline, reasoning setting, and vendor attribution; a configured legal or medical product must not be summarized as a new foundation model.
- **Frontier-lab internal pace metrics:** Treat automation shares, agent counts, monitor coverage, block/escalation rates, and safety-compute allocations as lab-reported operational snapshots, not industry-wide measurements. Record the date window, platform or workload scope, automation-level definitions, whether full autonomy was observed, and whether the classifier or judge was the lab’s own model. Keep compute denominators distinct (all compute, AI R&D compute, and AI-driven AI R&D compute), note short audit windows, and separate proposed third-party verification from verification already completed.
- **Plan and pricing announcements:** Verify plan names, effective date, included-limit percentage, credit amount, and whether access is included or metered. Distinguish annual-commitment pricing from month-to-month pricing, and state the billing condition next to each figure. For mixed-seat business plans, verify whether premium and standard seats can coexist in one workspace, each seat’s usage multiplier or time caps, minimum team size, and whether add-on credits remain separately metered. For claimed subscription freezes, distinguish an executive warning that sign-ups *may* pause from an enacted pause: inspect the live purchase UI and current official pricing/help pages, and state that no pause is confirmed when sign-up remains offered. Do not let a secondary article’s stronger wording override the primary statement or live product state. A live pricing page can confirm current seat names and feature differences while failing to render localized numeric prices in extracted text; in that case, verify exact prices against current same-event reporting rather than guessing from blank DOM fields. If the only announcement is on a forbidden social URL, use a compliant official pricing, documentation, or support page only when it genuinely helps verify the current offering; otherwise leave `URL:` blank rather than linking stale coverage.
- **Model retirements and migration notices:** Treat ChatGPT chat, specialized work surfaces, coding agents, enterprise workspaces, APIs, cloud-provider endpoints, and dated model snapshots as separate retirement scopes. Verify the exact model variant, retirement date, affected plans and surfaces, legacy-access period, conversation or project fallback behavior, recommended replacements, minimum client versions, and whether API access changes. Never infer an API deprecation from a consumer-product sunset or describe a recommended migration target as mandatory when alternatives remain available. For social-only notices on policy-blocked hosts, leave `URL:` blank unless current compliant coverage documents the same retirement; an older launch page may supply verified model-specific artwork but cannot serve as the event URL.
- **Executive departures and title drift:** Verify the executive’s role at the moment of departure, not merely the best-known historical title. Distinguish resigning from a current C-suite post from leaving the company after moving to special projects, an advisory role, leave, or another position. State tenure, effective timing, announced destination or reason only when sourced, and identify who had already assumed the responsibilities. Correct shorthand such as “COO resigns” to “former COO leaves” when the role changed earlier.
- **Board and safety-committee appointments:** Distinguish a voting director from a non-voting observer and a foundation/nonprofit board from the operating company’s board. Verify committee membership, governance scope, prior affiliations, current government roles, and stated recusals. When the primary announcement is on a policy-blocked host, use exact same-event compliant coverage as the final URL but prefer the primary announcement’s verified story image when its image host is allowed.
- **Researcher resignations over catastrophic-risk concerns:** Verify the person’s current role, prior lab history, work area, resignation timing, and whether they are leaving one company or the industry. When coverage combines several departures, map every quotation, probability, timeline, and “running out of time” warning to its actual speaker; do not assign article-level framing or one researcher’s statement to another researcher. Present extinction claims and accusations of irresponsible racing as personal assessments—not established capabilities or employer positions. Separate risks attributed to current models from hypothetical recursive self-improvement or future superintelligence, distinguish a colleague’s agreement from corporate endorsement, check for responses from named labs, and preserve uncertainty when they have not commented.
- **Funding announcements:** Distinguish one financing round from cumulative capital raised across seed, Series A, or other closings. Name lead investors separately from participants or strategic backers, and do not imply that every named investor led the round. Verify whether the headline amount is funding, valuation, debt, committed compute, or a mixed package. Normalize noisy pasted figures such as `$1,100,000,000.00` to `$1.1 billion` in the title and summary.
- **Reported acquisition agreements without company confirmation:** Do not rewrite “reportedly agreed to buy” as “buys” or “acquires.” Identify the outlet originating the report, distinguish an agreed deal from talks or a completed acquisition, and check whether either company has confirmed it. When secondary reporting cites both an agreement and anonymous confirmation that acquisition was merely part of recent talks, preserve the strongest shared fact with wording such as “reportedly agrees to acquire,” state that the companies have not confirmed the deal, and avoid implying closing. Prefer current same-event coverage with a verified canonical URL and image over earlier talks-only articles. Follow `references/acquisition-announcements.md`.
- **Synthetic-persona and simulated-user platforms:** Distinguish the advertised number of persona records from the number of agents actually instantiated and the number of evaluation trials performed. Report the released coreset, interaction environments, models, trial count, validation result, and stated limitations separately. Read the responsible-use section: simulated personas are not people or probability samples, and they do not remove the need to consult affected humans—especially for health, finance, employment, or other consequential decisions. Neutralize claims that companies can “skip user studies” unless the paper explicitly supports replacement rather than supplementation.
- **Automated alignment-research agents:** Separate the research agent, student or target model, monitoring model, and production baseline. Report the alignment-failure categories, benchmark family, metric definition (for example, percentage of safety gap closed), capability-preservation constraint, withheld-evaluation transfer, and target-model scale separately. Treat human comparisons cautiously when agents could iterate but humans could not. Include cheating-monitor results and material limitations: narrow proxy benchmarks, unmeasured capability regressions, incomplete monitorability, and no guarantee that gains survive later training. Frame results as evidence for an assisted research workflow—not proof that alignment is solved or that autonomous systems can safely align successors without oversight.
- **Bare topic or pasted claim:** Search the exact wording first, then confirm it against the original source or a live product page. If the exact term produces only unrelated results, ask one short clarification and offer a plausible spelling correction only as a tentative candidate; after terse confirmation, research the corrected term and continue without another question. Correct misleading shorthand and product category silently in the neutral title and summary while preserving the underlying news value. If the same intake is pasted repeatedly, treat it as one request and return one item. Follow `references/ambiguous-topics-commerce-and-benchmarks.md` for bare-name disambiguation, agentic-commerce safeguards, conversational benchmarks, and paper-image fallbacks.
- **Adjacent product surfaces with similar names:** Do not force the user’s shorthand onto the current announcement when a vendor has several similarly named surfaces (for example, Claude Desktop versus Claude Code). Inspect the dated primary announcement and state the exact surface in the title. In the summary, briefly distinguish an older related integration only when needed to prevent the shorthand from becoming a false launch claim. For third-party model gateways, verify whether the integration supports local models, hosted models, or both; how users switch back to the vendor’s models; and whether telemetry or retention claims apply to the local runtime, hosted service, or both. Prefer the current event URL and a current settings/model-selection screenshot over older coverage.
- **Cross-surface coding-session continuation:** Distinguish resuming a saved session, transferring or teleporting it, remotely controlling the same process, and starting a new session from a generated summary. Verify the source and destination surfaces (CLI, desktop, IDE, web, or mobile), the exact command or UI entry point, whether the full transcript and tool state or only a summary transfers, project-directory requirements, and whether local changes move with the conversation. Do not use a generic product page or adjacent “continue in another surface” documentation as the final URL unless it explicitly documents the newly announced direction of transfer; for social-only updates, leave `URL:` blank and use verified product art.
- **Political or executive technology slogans:** Verify the exact subject and surrounding policy context before repeating a compressed claim. Distinguish AI models from the infrastructure supporting them—for example, “data centers could be bigger than oil” must not become “AI is bigger than oil.” Identify who said it, where, what action or dispute prompted it, and material infrastructure concerns such as power, water, grid reliability, permitting, or tax incentives.
- **AI protests and activist stunts:** Neutralize loaded verbs such as “stormed,” “invaded,” or “occupied” unless reporting establishes forced entry, obstruction, confrontation, or sustained control of the premises. Verify the exact office and city, whether participants entered a public lobby or restricted workspace, the organizer and stated demand, costumes or performance elements, arrests, injuries, property damage, duration, and any company response. If organizers are unidentified, say “demonstrators” or “activists” rather than assigning them to a known movement. Treat mocking or ideological commentary in social-search synthesis as noise; describe the action and message without adopting “cringe,” “cult,” “LARP,” or similar reactions unless public reaction itself is the requested story.
- **ChatGPT Sites analytics:** Distinguish per-Site traffic analytics from Enterprise/Edu workspace analytics. Inspect `learn.chatgpt.com/docs/sites` as verification evidence for automatic tracking without an SDK, unique visitors, page views, time-series controls, and availability through ChatGPT web/desktop rather than CLI or IDE extension. The final learn-more URL must still pass `anf_policy`; use compliant coverage or leave `URL:` blank.
- **Desktop activity-history and ambient-memory features:** Inspect the exact official documentation as verification evidence, then choose a final learn-more URL that passes `anf_policy`; if no compliant current coverage exists, leave `URL:` blank. Verify platform, eligible plans, geographic exclusions, workspace-admin requirements, personal opt-in, dependency on existing memory settings, event types collected, local-versus-shared storage, pause/exclusion/deletion controls, and prompt-injection warnings. Distinguish interaction-event capture from screenshots, screen recordings, microphone input, and system audio; do not describe the feature as continuous screen recording when the documentation explicitly excludes those media. A feature-specific official OpenGraph image may still be used if it passes the separate image policy and resolves directly.
- **Pasted plan / access announcements without a durable public page:** If the user pastes pricing or rollout copy (plan names, % of limits, credit amounts, effective dates) and search only finds stale prior notices or social posts, do **not** stretch an old launch/redeploy article into the current change. Use a live pricing/docs page only when it actually reflects the claim; otherwise leave `URL:` blank and pair with related official product art. Still report plan names, effective date, included-limit %, and credit amount accurately from verified pasted text.
- **`.ai` and other policy-blocked official hosts:** Domains ending in `.ai` (e.g. `x.ai`, `platform.kimi.ai`) and hosts in `forbidden_url_domains` cannot be final URLs even when they are the primary source. Prefer Microsoft Marketplace / app-store listings, official GitHub org/repo, independent press, or a non-`.ai` company site. If none exist, leave `URL:` blank; still use a compliant story-specific image.
- **Grok / SpaceXAI Microsoft integrations:** First distinguish standalone Office add-ins, model choice inside Microsoft 365 Copilot, Copilot Studio external models, Microsoft Foundry models, and GitHub Copilot. For standalone Excel/Word/PowerPoint add-ins, prefer the Microsoft Marketplace listing over `x.ai/grok/*`; for a Microsoft 365 Copilot rollout, verify the exact app surfaces, preview program, administrator opt-in, hosting/data boundary, safety notices, and regional exclusions against current Microsoft documentation and same-event coverage. Never use an older Copilot Studio, Foundry, GitHub Copilot, or add-in page as proof of a new in-app Copilot rollout. Follow `references/grok-product-surface-verification.md`.
- **Research papers:** Normalize obvious arXiv URL typos (for example, `alphavix.org/abs/<id>` when the identifier matches arXiv syntax) to `https://arxiv.org/abs/<id>`, then verify that the canonical page resolves to that exact paper before using it. Read the abstract and, when available, the HTML paper—not just coverage. Use the arXiv Atom API to recover ambiguous or stylized titles, verify original-versus-revision dates, and count/inspect authors rather than trusting viral copy. Extract paper figures together with their captions from the rendered HTML and choose the figure that directly represents the reported result. Describe findings as author-reported rather than settled fact, and read limitations/responsible-use sections before summarizing. For consciousness or sentience research, distinguish shifts in model activations, self-reports, or survey responses from evidence that a model is conscious; state that limitation when headlines could invite the stronger interpretation. Follow `references/research-and-provenance-verification.md`.
- **AI-generated text watermarks and file provenance:** Separate model-level text watermarks from C2PA or other signed file metadata. Verify which models, release dates, products, APIs/cloud surfaces, and geographies are covered; do not generalize “new supported models” into “all generated text.” Note that copied text may retain a mark, but short passages or heavy editing can defeat detection. A detected mark does not prove the underlying content was authored by AI, and an absent mark does not prove human authorship. Distinguish legal requirements from voluntary code commitments. Follow `references/research-and-provenance-verification.md`.
- **AI-designed genomes, organisms, and viruses:** Separate sequence generation from chemical synthesis and demonstrated biological function. Verify the model, training-data scale, natural scaffold or lineage, number of designs tested versus functional results, host range, and whether the constructs can infect humans. For bacteriophages, say explicitly that they infect bacteria rather than people; do not generalize a small lab result into arbitrary organism design. Report therapeutic potential and material biosafety/biosecurity concerns without implying that a human pathogen was created. When the main article is paywalled, follow its cited DOI and credible linked coverage to verify these details while retaining the strongest compliant article URL and story image.
- **Virtual-cell and biological world models:** Distinguish a genuinely unified, stateful simulator from a pipeline or ensemble of specialist models. Verify which biological scales are represented (DNA, RNA, proteins, regulatory networks, phenotype), whether interventions propagate through a persistent state, supported cell lines, benchmark provenance, and demonstrated scale. Separate reproduction of established biology or held-out data from prospective wet-lab validation of novel predictions. Preserve preview status and explicit fidelity limits; do not call the system a digital twin, whole-organism simulator, or reliable drug-discovery engine unless the evidence establishes that scope. When the official launch host is policy-blocked (such as a `.ai` domain), prefer exact same-event independent coverage and its verified story image.
- **Agent-harness launches and benchmark claims:** Distinguish the managed harness from the underlying model and state which responsibilities the provider manages—sessions, orchestration, context compaction, recovery, tools, and subagents—versus what the developer supplies. Verify execution choices separately (provider-hosted sandbox, partner environment, or self-managed infrastructure), public-beta versus general availability, usage charges beyond any “no additional API fee” claim, and material residency or retention limits. Preserve the exact benchmark variant, metric, aggregation (for example Best@1 versus Best@3), model, score, comparison baseline, and run-to-run range when available. Attribute self-reported results to the team and do not generalize one benchmark into overall intelligence. If the official launch article is on a policy-blocked `.ai` domain but the project is open source, use the verified official GitHub repository as the final URL; the launch article may still supply a policy-compliant story image and technical evidence.
- **One-conversation project orchestration:** Distinguish a coordinator that decomposes one project into parallel worker threads from agent view (the user dispatches independent sessions), agent teams (coordinated sessions with shared tasks), dynamic workflows (scripted or generated high-fan-out execution), and ordinary cloud sessions. Verify who creates and supervises the threads, whether workers share context or files, whether the parent synthesizes one result, where execution runs, whether work survives closing the browser or laptop, eligible plans, preview status, and rollout scope. Do not use older documentation for an adjacent parallel-agent feature as the event URL when it does not describe the announced orchestration mode; leave `URL:` blank and use verified related product art instead.
- **Orbital AI-compute announcements:** Treat planned satellites and constellations as development programs, not deployed infrastructure. Verify whether the companies are jointly designing a payload or merely supplying hardware; identify the announced GPU/CPU platform, prototype-versus-production dates, intended orbit and workload, regulatory status, and whether launch or mass-production schedules are conditional. Avoid implying demonstrated data-center performance before an orbital prototype exists.
- **Emerging hardware, robot production, and autonomy claims:** Separate autonomous AI behavior from teleoperation, remote human control, demos, scripted routines, and conventional automation. For robot “zero-shot” or unseen-environment claims, identify exactly what was unseen (rooms, layouts, objects, or tasks), what was pretrained, and what task-specific fine-tuning occurred elsewhere; never turn “no adaptation in evaluation homes” into “the tasks were never trained.” Record the number and type of environments, whether one fixed checkpoint was used, intervention/time-out rules, and whether success required the complete task or allowed partial credit. Compare pretrained and scratch baselines only when task data, architecture, optimization, and evaluation were held fixed, and attribute priority, scaling-law, and performance claims to the company unless independently reproduced. For factory launches, distinguish design takt time (“one unit every X minutes”), planned annual capacity, production-line startup, sustained measured output, and delivered units; attribute “world’s first” and company production-rate claims unless independently audited. For surveillance-style demonstrations, distinguish sensors, obstacle avoidance, path planning, and plausible mission fit from an announced operational deployment; verify the venue, developer, tested depth/speed, endurance, payload, operator role, and whether autonomy was demonstrated or merely listed in a catalogue. For pre-orders, verify the advertised price, deposit versus total cost, ship window, geography, current order status, hardware specifications, and whether showcased tasks are demonstrations or promised general capabilities. Neutralize slogans such as “teach it anything.” Verify road legality, deployment status, speed/range, and whether a capability is shipping or merely demonstrated. Product renders or company illustrations should not be mistaken for operating prototypes.
- **Domestic-robot services:** For home-cleaning or household-helper claims, verify service area, price, invitation/waitlist status, supported chores, required customer supervision, and whether the robot is autonomous, AI-assisted, or teleoperated. Inspect service and privacy terms for in-home video, spatial maps, telemetry, retention, licensing, model-training use, and deletion limits. State autonomy status explicitly and summarize material privacy trade-offs without sensationalizing them.
- **Speculative breakthrough headlines:** Neutralize claims such as “obsolete,” “revolutionary,” or “replaces data centers.” State the current technical limitation, cost, or research maturity preventing the headline outcome today.
- **AI-assisted clinical-trial breakthroughs:** Separate a company-reported top-line result from peer-reviewed or conference-presented data, regulatory approval, routine availability, and a cure. Verify trial phase, enrollment, randomization, control arm, disease stage, intervention, primary and secondary endpoints, whether the analysis was interim or final, and whether effect sizes, confidence intervals, safety, quality-of-life, and overall-survival data have actually been released. Do not reuse Phase 2 percentages as though they were Phase 3 outcomes. Attribute “first positive Phase 3” and similar priority claims to named experts or sources, and neutralize forecasts that cancer will be cured within a few years. For personalized therapies, distinguish tumor sequencing and algorithmic target selection from a demonstrated AI contribution; use “AI-assisted” only when the source documents the AI system’s role. State material pending steps, such as full data presentation, regulatory review, and long-term follow-up.
- **Viral AI metaphors and unlabeled charts:** When a public figure repeats a slogan such as “AI is a supersonic tsunami,” identify the specific current post and date rather than conflating it with older uses of the same phrase. Inspect any attached chart for axis labels, units, source, and metric. If the y-axis or underlying data is missing, say the chart appears to depict rapid growth but cannot establish whether it represents capability, spending, revenue, adoption, or another measure. Use neutral independent coverage as the compliant URL when the original social post is policy-blocked.
- **Open-weight model launches (vendor scale claims):** Prefer API/docs rewrite targets or strong independent coverage when the official host is `.ai`. Attribute “largest,” “first 3T-class,” and “second only to X” as company claims; separate API-live from weights-not-yet-released dates. For Hugging Face releases, verify the official organization repository through `/api/models/<org>/<model>`: confirm `private:false`, `gated:false`, current `lastModified`, license metadata, actual weight shards in `siblings`, and `usedStorage`. A model page may exist before weights arrive, so repository creation alone does not prove release. Read the raw `README.md` for architecture and context claims, report total versus activated parameters separately, and describe custom-license releases as **open-weight**, not automatically open-source. Frame vendor-produced demonstrations as company-produced experiments, distinguish marketing claims from independently verified results, and do not declare a winner or operational outcome unless the transcript, video, or description supports it.
- **Map-based browser games and geographic-data demos:** Treat phrases such as “Google Maps as a game” or “drive any street” as analogies until verified. Inspect the official product and credible coverage to identify the actual map, road, elevation, satellite, or Street View providers; do not attribute OpenStreetMap or topographic data to Google Maps. Distinguish procedurally generated roads and terrain from imagery-based Street View driving, and preserve early-access or experimental status. Dynamic game sites may expose no useful OpenGraph image; in that case, keep the official game URL but use a visually verified, story-specific gameplay image from credible coverage rather than a generic logo or control overlay.
- **“AI solved / disproved theorem” claims:** prefer science press; soften title until verification is clear; credit human researcher plus model helper; note ongoing scrutiny when appropriate.

## Persistent ANF Queue

After the final policy-compliant four-line block is ready, but before returning it to the user, queue that exact block:

1. Use `execute_code` with `terminal` and shell-quote both multiline arguments so content is passed safely. Prefer the built-in `shell_quote`; if it is unexpectedly unavailable in the sandbox, fall back to Python’s `shlex.quote` rather than changing the queue command or passing raw multiline text.
2. Run `python3 ~/.hermes/skills/communication/compile-anfs/scripts/anf_queue.py add --content <shell-quoted-block> --source <shell-quoted-publication-name>`. The publication name must identify the source used for the item (for example, `Reuters`, `The Verge`, or `arXiv`) and is stored for the GitHub JSON export.
3. Require JSON status `queued` or `duplicate`, capture the returned record ID, then read back that ID from `~/.hermes/data/anf-queue/records.jsonl` and compare its `block` field (or SHA-256) with the exact final block. The queue CLI does not expose a record-level `get` command, so do not invent one; parse the JSONL deterministically in the same `execute_code` call. If execution is interrupted by an approval prompt or timeout, inspect queue state for the exact block before retrying so an ambiguous write is not mistaken for a failed one. Treat the ANF as unfinished until read-back succeeds; retry insertion once only when the record is absent, and do not claim it is unqueued without checking.
4. Queue each distinct block separately and in response order when handling multiple ANF intakes.
5. Do not mention queue bookkeeping in the ANF response; the visible response must remain only the required four-line block(s).

The companion `compile-anfs` skill creates a single text file containing every queued record after its persistent checkpoint.

### Chief of Staff and Automated ANF Intakes

For ANFs received through the user's Chief of Staff bridge:

1. Show the inbound JSON payload in the user's Telegram before processing so the intake is visible.
2. Treat an `anf_v1` payload containing complete `title`, `description`, `image_url`, and `learn_more_url` fields as already researched and editorially finalized by the upstream LLM. Mechanically map those fields into the four-line ANF block without researching, rewriting, retitling, summarizing, or substituting URLs. Apply only structural validation and durable queue insertion; preserve empty fields exactly. This trusted preprocessed path overrides the normal research and rewriting workflow.
3. Before enabling or changing the route, run a realistic signed ANF through its isolated session and verify that the route exposes every capability needed for durable insertion and any non-preprocessed intake work. Telegram delivery belongs to the webhook dispatcher; do not make processing depend on the model having a messaging tool.
4. For incomplete or non-`anf_v1` webhook requests, research, format, validate, and queue the ANF in the webhook's isolated processing session exactly as for a direct intake.
5. Put a fail-closed ANF validator at the actual final outbound boundary used by the automated intake—not only in an upstream/source adapter or an adapter the route bypasses. Detect exact four-line ANF blocks, insert them idempotently, read back the exact block/hash, and block delivery if queue validation fails; this prevents a model from bypassing queueing while still emitting a polished ANF.
6. Treat an error-only or non-ANF final response to an accepted ANF request as an unresolved intake. Surface it for recovery and prevent the next compilation from silently passing merely because no four-line block was produced.
7. After queue validation succeeds, deliver the finished four-line block directly to the user's Telegram; do not reply to the Chief of Staff or make Telegram delivery depend on an upstream callback succeeding.
8. Verify queue insertion and Telegram delivery as separate outcomes. A visible raw payload proves receipt only, while a queue record proves processing only; neither proves that the finished ANF appeared in Telegram.

Queue boundaries:

- Treat hypothetical compilation questions—such as “if I compiled now” or “what would be included”—as read-only previews, not delivery triggers. Inspect queue status and list records with IDs greater than `last_exported_id` in ascending ID order; do not prepare, deliver, or advance the checkpoint.
- A new installation starts with an empty queue; never guess whether older Telegram ANFs were already copied. Import history only from an explicitly chosen cutoff/date/message range.
- For a user-specified cutoff item, exclude the cutoff itself and import later finalized four-line ANF outputs in chronological order. Search all stored Telegram sessions in the active Hermes profile, not merely the current conversation; clearly distinguish stored Hermes history from raw Telegram history that Hermes never recorded.
- Treat an exact duplicate as retry noise. For a correction that is still pending, preserve the intended revised item rather than knowingly exporting both versions; do not rewrite already-delivered history.
- Export is a two-phase transaction: prepare one immutable pending batch, deliver that exact file to Telegram, and advance the checkpoint only after the Telegram API accepts the attachment. A failed delivery must leave the same batch pending for retry.
- If the user says the last file he actually received predates the queue checkpoint, reconcile the last cron output, queue `state.json`/`last_export_path`, and the Telegram session transcript before claiming there were no new items. A manual run may have advanced the checkpoint. Recover by reattaching the immutable file at `last_export_path` in the current conversation; do not rerun delivery, acknowledge again, or republish GitHub JSON. State plainly that the existing `.txt` was resent and GitHub was not reuploaded.
- Follow `references/checkpointed-export-queue.md` for storage, historical imports, delivery acknowledgement, recovery, and isolated-test details.

## Final Intake and Policy Gate

Immediately before queueing and returning each block, perform this gate. For a complete Chief of Staff `anf_v1` payload, use the trusted preprocessed exception above: verify structure and queue parity only, without changing any supplied editorial field or URL.

1. **Intake isolation:** Confirm the block answers a distinct user intake from the current turn. Discovery may surface adjacent releases, but never research, queue, or return them unless the user requested them. One intake produces one block unless the user supplied multiple distinct items.
2. **Final URL validation:** Re-check the literal final `URL:` hostname and suffix against `metadata.hermes.anf_policy`; do not rely on having checked an earlier candidate. If an official `.ai` page exposes a compliant canonical mirror, use that mirror only after verifying it is authoritative and current; otherwise choose compliant coverage or leave the URL blank.
3. **Image validation:** Re-check the literal image hostname against the image policy and verify that it resolves directly to an image.
4. **Claim alignment:** Ensure the chosen URL documents the current event—not merely an earlier announcement, preview, or adjacent product.
5. **Queue parity:** Queue exactly the final block that will be returned. Never queue exploratory, discarded, or adjacent-news blocks.

## Pitfalls

- Do not include analysis notes, caveats, or explanations outside the four lines.
- Do not exceed 60 words in the summary.
- Do not leave `Image URL:` as unavailable or placeholder text.
- Do not blindly use tracking parameters; canonicalize article URLs when possible.
- Treat superlatives such as “first,” “best,” or “most advanced” as attributed company claims unless independently verified; neutralize them in the title and use “the company calls/claims” in the summary.
- Distinguish announcement, unveiling, launch, availability, and shipment dates; do not turn a scheduled or limited release into general availability. API live ≠ open weights shipped.
- For unreleased products or models, seek credible independent reporting, label specifications as reported or rumored, and state when the company has not officially confirmed them.
- For screenshots, extract visible text first, then verify with search when possible.
- Do not use `x.ai`, `platform.kimi.ai`, or other `.ai` product pages as `URL:` even when the user pastes them; rewrite to a compliant alternate or leave blank.
- Branding drift: marketplace and some coverage may say “SpaceXAI” for Grok Office add-ins while other sources still say xAI—mirror the listing you cite, neutrally.
